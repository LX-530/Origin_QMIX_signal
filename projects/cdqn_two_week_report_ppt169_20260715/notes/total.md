# 01_cover

这份汇报的结论很克制：我们已经把级联 DQN 的最小工程路径跑通，但还不把它包装成优于 QMIX 的最终结论。今天重点说明三件事，第一是当前代码到底是什么状态，第二是我们如何把 Cascading DQN 思想迁移到信号控制，第三是哪些结果已经验证、哪些结果必须等服务器全量实验回填。

---

# 02_core_question

这个问题不能简单理解成“QMIX 不行，所以换 CDQN”。当前仓库实际可见的是十八个智能体，同时原训练配置里 epsilon 退火过快、训练更新次数过少，这两点本身就足以导致不稳定。因此本阶段先建立一个修正后的 QMIX 基线，再实现 CDQN 最小版本，保证后续对比是公平的。

---

# 03_environment_audit

审计结果显示，当前环境真实维度是十八个智能体、四个动作、七十二维全局状态和一百三十六维观测，episode 上限是一百五十步。更关键的是，动作 mask 是硬约束，非法动作会直接造成 KeyError；因此无论是探索还是贪心选择，都必须只在合法动作中进行。训练风险主要集中在 epsilon 退火和更新次数，而不是算法名称本身。

---

# 04_paper_insight

Cascading DQN 对我们的启发，是把组合动作从一次性枚举变成依次选择。原来如果直接看二十四个信号、每个四个动作，搜索空间最多是四的二十四次方；级联后每个位置只评估四个候选，复杂度变成二十四乘四。这个思想能降低动作选择难度，但需要注意，本项目不是推荐列表选择，不同信号可以选择相同动作编号。

---

# 05_project_adaptation

所以我们采用的是 CDQN-style autoregressive DQN，而不是论文原算法的完全复现。论文里选择的是不重复的推荐物品，本项目里每个信号都要各自选择动作，动作编号可以重复，真正不能放松的是每个信号自己的 action mask。这个命名上的谨慎很重要，可以避免后续汇报时被质疑理论前提不一致。

---

# 06_network_td_target

网络设计遵守最小可行原则。状态先进入共享编码器，然后把 agent 位置 embedding 和前一个动作 embedding 送入 GRU 级联核心，最后用 Q head 输出当前信号四个动作的 Q 值。训练目标采用 Double DQN，用 online 网络选择下一步联合动作，用 target 网络估计目标值，并用 Huber loss 降低异常 TD 误差的影响。

---

# 07_code_changes

工程上没有破坏原来的 QMIX 路径，而是新增 cascade_dqn 路径。新增文件包括级联网络、策略、transition replay buffer、单进程 runner、冒烟测试和对比脚本；原有入口只增加算法路由、参数 preset、reward_norm 开关和统一评估日志。这样后续可以在同一个仓库里并行比较原 QMIX、修正 QMIX 和 CDQN。

---

# 08_verified_results

本地验证已经证明训练闭环是通的：环境冒烟测试没有非法动作，CDQN 用九百个环境步可以端到端训练，loss 从约零点零二八下降到约零点零一七，模型和 CSV 指标都能保存。与此同时，已有 compare 曲线只有很少的评估点，只能说明脚本可用，不能当成正式性能证据，所以这页故意不放曲线。

---

# 09_two_week_deliverables

两周工作量应该按成果呈现，而不是按天数堆任务。最小成功版本包括环境审计、修正 QMIX 基线、CDQN 最小实现、奖励归一化、指标日志和可替换的汇报材料。真正高风险的部分是二十四智能体定义，因为当前仓库没有完整的 agent cell、动作映射和 mask，必须先补齐这些信息。

---

# 10_decision_next_step

最后的决策规则很明确：CDQN 已经值得进入二十四智能体版本验证，但还不能宣称优于修正 QMIX。下一步先补齐二十四个信号的定义，然后在服务器上用同预算、至少五个 seed 比较原 QMIX、修正 QMIX 和 CDQN。只有在完成率不差、疏散步数更短、火灾暴露不恶化且方差更小的情况下，才建议替换 QMIX。
